# DecisionPassport

**Цифровой контур принятия управленческих решений для предприятия атомной отрасли.**

Платформа реализует научный результат магистерской диссертации «Совершенствование процессов принятия управленческих решений в системе корпоративного управления предприятием атомной отрасли в условиях цифровой трансформации» (НИЯУ МИФИ, 2026). Эмпирическая база — АО «НАК «Казатомпром».

Единица управления в системе — не документ и не отчёт, а **управленческий вопрос**, получающий полный цифровой след: инициатор, цель, данные с указанием источника, альтернативы, риски, расчёты, согласования, решение, поручения, фактический результат и извлечённые уроки. Этот след материализуется в объекте «Цифровой паспорт управленческого решения».

---

## Три принципа, зашитые в код и UX

| Принцип | Как обеспечен технически |
| --- | --- |
| **Human-in-the-loop.** Система не принимает решение за человека | Переход со стадии «Решение» невозможен, пока `status ≠ APPROVED` ([lib/gate-service.ts](lib/gate-service.ts)); утверждение требует явного выбора альтернативы и мотивировки от роли `BOARD_MEMBER`; ни одно предложение ИИ не применяется без вердикта человека (`AiSuggestion.humanVerdict`), «Отклонить рекомендацию» — равноправная кнопка |
| **Сначала данные и процесс — затем интеллект** | Аналитическая ступень ИИ открывается только для показателей с заполненными источником и владельцем; рекомендательная — только при наличии валидированной модели в реестре, допущенной для данного уровня критичности ([lib/ai/eligibility.ts](lib/ai/eligibility.ts)) |
| **Прослеживаемость.** Любое число кликабельно до источника | Компонент [components/provenance.tsx](components/provenance.tsx) у каждого значения раскрывает систему-источник, дату актуальности, владельца и формулу; карточка показателя содержит граф происхождения данных |

## Запуск

```bash
npm install
npm run db:push     # создание схемы БД (SQLite по умолчанию)
npm run seed        # демо-данные: 9 пользователей, 12 решений, 20 показателей
npm run dev         # http://localhost:3000
```

Приложение **полностью работает без единого внешнего API-ключа**: при отсутствии `AI_API_KEY` используется детерминированный `MockProvider`, строящий ответы из данных паспорта.

Прочие команды:

```bash
npm run typecheck      # TypeScript strict, без any и @ts-ignore
npm run lint           # ESLint
npm run test           # Vitest: 77 юнит-тестов
npm run test:e2e       # Playwright: сквозной сценарий уровня A
npm run build          # production-сборка
```

### PostgreSQL вместо SQLite

Схема написана переносимо (перечисления хранятся как `String`, а не как Prisma-enum). Для перехода:

1. в [prisma/schema.prisma](prisma/schema.prisma) заменить `provider = "sqlite"` на `provider = "postgresql"`;
2. в `.env` указать `DATABASE_URL="postgresql://user:pass@localhost:5432/decision_passport"`;
3. выполнить `npm run db:push && npm run seed`.

Код приложения менять не требуется.

### Ключевые архитектурные решения

1. **Ворота — чистые функции.** Правила в [lib/gates.ts](lib/gates.ts) работают над снимком решения (`GateSnapshot`) и не знают о БД, поэтому покрыты юнит-тестами целиком. Таблица `GateCheck` хранит только *применимость* правила (переход × уровень критичности × блокирующее ли), а сами проверки — код. Администратор меняет конфигурацию через `/admin`, не трогая логику.
2. **Единственная точка перехода** — `POST /api/decisions/:id/advance`. UI не решает, можно ли двигаться дальше: он показывает чек-лист, а допуск определяет сервер.
3. **Мутации через server actions** с единым контрактом `ActionResult` (`{ok:true}` / `{ok:false, error}`), проверкой прав и записью `AuditEvent` в той же транзакции.
4. **Полнота блоков вычисляется, а не хранится «на веру»** — из фактического содержимого паспорта ([lib/snapshot.ts](lib/snapshot.ts)); поле `completeness` лишь кэширует расчёт.
5. **Деньги считаются только из введённых параметров.** Функции эффекта возвращают либо результат, либо `{ok:false, missing:[...]}`; интерфейс выводит «Недостаточно данных для расчёта» с перечнем незаполненных параметров, но никогда — оценку по умолчанию.
6. **Разделение природы числа.** Три визуально различных бейджа: факт, прогноз, допущение. Прямой и косвенный экономический эффект разделены визуально; к риск-эффекту применяется консервативный коэффициент атрибуции (по умолчанию 0.5) с обязательным полем обоснования.
7. **Индекс зрелости всегда с контекстом.** В коде нет пути, где он выводится без размера выборки, периода, перечня учтённых KPI и пометки «расчёт по данным пилота — не официальный показатель компании».

## Тестовое покрытие

**Vitest — 77 юнит-тестов:**

- `tests/effects.test.ts` — три формулы эффекта, включая поведение при незаполненных параметрах;
- `tests/gates.test.ts` — все 11 правил контрольных ворот и их применимость по уровням A/B/C;
- `tests/maturity.test.ts` — нормирование KPI и расчёт индекса зрелости;
- `tests/authz.test.ts` — матрица прав по всем ролям.

**Playwright — сквозной сценарий уровня A:** вход инициатором → создание паспорта → попытка двинуться к принятию решения без альтернатив блокируется с объяснением, чего не хватает и кто отвечает → добавление альтернатив со «статус-кво», допущений и риск-профиля → подтверждение качества данных владельцем → независимая проверка расчёта вторым пользователем → принятие решения членом СД с мотивировкой → поручение с KPI → пост-оценка → запись урока в базу знаний → проверка, что аудит зафиксировал все мутации.

## О демо-данных

- Показатели **внутри паспортов решений** (трудоёмкость, вероятности, суммы потерь) — **синтетические**; в интерфейсе они помечены бейджем «демо-данные».
- **Публичные показатели компании** на дашборде — из интегрированного годового отчёта АО «НАК «Казатомпром» за 2025 год и помечены ссылкой на источник ([lib/company.ts](lib/company.ts)).
- Система нигде не показывает «фактический» финансовый эффект, не выведенный из введённых пользователем параметров.

Проектные решения и их обоснования зафиксированы в [DECISIONS.md](DECISIONS.md), декомпозиция работ — в [PLAN.md](PLAN.md).
